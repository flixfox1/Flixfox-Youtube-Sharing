# Unified Coordinate System Design (Merged Design)

> Based on a merger of two independent analyses from Codex and Gemini, combined with a review of the actual project codebase
> Reviewed and revised by the Refactoring Architect
> Purpose: The single reference document for implementation

---

## Background

The project has three layers of coordinate spaces:

```
Screen (e.clientX/Y) ──→ Canvas/World (infinite canvas) ──→ Local (relative to parent Group)
       CameraController          TransformService
```

Both transformation layers suffer from shotgun-style duplicate implementations:

**Local ↔ World (TransformService layer)**: The conversion logic has 6 independent implementations. `TransformService` already provides a complete matrix transform API (`getFullWorldTransform`, `localToWorld`, `worldToLocal`), but none of the 4 consumers in the View layer use it — all hand-write simplified versions. The root cause is that `TransformService` returns a `Mat2x3` matrix, which feels heavy for scenarios that only need x/y offsets, and lacks a lightweight convenience API. The current `CanvasEditor.getShapeWorldPosition()` uses simple `bounds.x/y` accumulation, which is correct without rotation but will completely break once Group rotation is enabled.

**Canvas ↔ Screen (CameraController layer)**: `CameraController` already provides `screenToCanvas()` and `canvasToScreen()`. The Screen→Canvas direction (input) is compliant — all pointer event entry points correctly call `camera.screenToCanvas()`. However, the Canvas→Screen direction (output) has 5 places that inline `x * zoom + panX`, none of which call `camera.canvasToScreen()`. Additionally, `CameraController` lacks a `getVisibleWorldBounds()` public method, causing `Minimap.tsx` to inline the visible area calculation.

---

## Design Principles

1. The underlying layer strictly uses matrix multiplication; convenience APIs are just projections of matrix results, not independent computation paths
2. Do not expose intermediate values (offsets); only expose transformation results
3. Non-breaking additions — do not change the existing `getFullWorldTransform()` signature
4. All Local ↔ World calculations must and can only go through `TransformService`
5. All Canvas ↔ Screen calculations must and can only go through `CameraController`
6. `TransformService` does not depend on `CameraController`; cross-layer composition is only done in the View layer's `coordHelpers.ts`

## Layer 1: Fill in Convenience APIs (Execute Immediately)

### Adopted API Design

Add the following methods to `TransformService`:

```typescript
// Returns the AABB bounding box of a shape in world coordinate space
getWorldBounds(shapeId: MShapeId): Rect;

// Converts a point in the shape's local coordinate space to a world point
localToWorld(point: Vec2, shapeId: MShapeId): Vec2;  // already exists, no need to add

// Converts a point in world coordinate space to the shape's local coordinate space
worldToLocal(point: Vec2, shapeId: MShapeId): Vec2;  // already exists, no need to add
```

`TransformService` already has `localToWorld` and `worldToLocal`. The only truly missing method is `getWorldBounds`.

> ⚠️ **Review Revision: `localToWorld` / `worldToLocal` have an implementation bug**
>
> The existing `localToWorld` and `worldToLocal` signatures are correct, but their internal implementations use `getWorldTransform()` (rotation only, no position offset) instead of `getFullWorldTransform()` (position + rotation). For Group children, `getWorldTransform` drops all ancestor position offsets, producing completely wrong results.
>
> This must be fixed in the current round of work: change the implementations of `localToWorld` and `worldToLocal` to use `getFullWorldTransform()`. This is a prerequisite for all subsequent migrations — otherwise consumers migrated to `localToWorld()` will still get wrong results for Group children.

### `getWorldBounds` Implementation

> ⚠️ **Review Revision: original implementation has a double-calculation bug, now corrected**
>
> The matrix chain of `getFullWorldTransform(shapeId)` already includes `matTranslate(bounds.x, bounds.y)` inside `getFullLocalTransform` — meaning the matrix already maps the shape's local origin `(0,0)` to the correct position in world space. If `(bounds.x, bounds.y)` is then passed as the input point, the position offset is applied twice. The four corners of the shape's local space should be `(0,0)` → `(width, height)`, not `(bounds.x, bounds.y)` → `(bounds.x+width, bounds.y+height)`.

```typescript
getWorldBounds(shapeId: MShapeId): Rect {
  const shape = this.store.getShape(shapeId);
  if (!shape) return { x: 0, y: 0, width: 0, height: 0 };

  const { width, height } = shape.bounds;
  const mat = this.getFullWorldTransform(shapeId);

  // Local space corners: (0,0) → (w,h), NOT (bounds.x, bounds.y) → (bounds.x+w, bounds.y+h)
  // because getFullLocalTransform already includes matTranslate(bounds.x, bounds.y)
  const pts = [
    matApply(mat, { x: 0, y: 0 }),
    matApply(mat, { x: width, y: 0 }),
    matApply(mat, { x: 0, y: height }),
    matApply(mat, { x: width, y: height }),
  ];
  const xs = pts.map(p => p.x);
  const ys = pts.map(p => p.y);
  const minX = Math.min(...xs), minY = Math.min(...ys);
  const maxX = Math.max(...xs), maxY = Math.max(...ys);
  return { x: minX, y: minY, width: maxX - minX, height: maxY - minY };
}
```

### Decision on `getAncestorOffset`: Not Adopted

Codex suggested providing `getAncestorOffset(parentId): Point` as a convenience API for "translation-only" scenarios. This is not adopted for the following reasons:

1. `ShapeRecord` already has a `rotation` field, and Group rotation is a clear future direction. Exposing an "offset" API will immediately cause misuse once Group rotation is enabled — the same class of error as the current `getShapeWorldPosition()` simple accumulation
2. The current `CanvasEditor.getShapeWorldPosition()` is exactly this pattern: correct without rotation, but fundamentally a time bomb. Adding a similar API creates a second time bomb
3. Gemini's argument is correct: when a parent Group rotates 90°, a child at `(100, 0)` has a world offset of `(0, 100)`, not `(100, 0)` — simple accumulation cannot handle this
4. On performance, Codex's idea of "skipping full matrix multiplication and reading the translation component directly" has value, but should be implemented as a caching optimization inside `getFullWorldTransform`, not exposed as a separate API

### Disposition of `getShapeWorldPosition`

`CanvasEditor.getShapeWorldPosition()` is the most dangerous method in the current project — it simulates matrix transforms with simple accumulation, happens to be correct without rotation, but will completely break once Group rotation is enabled. Disposition:

> ⚠️ **Review Revision: do not mark `@deprecated`, replace + delete directly**
>
> The original plan's "delegate + mark deprecated + gradual migration" strategy conflicts with the project's Big Bang refactoring principle — steering rules explicitly state "No adapters, no gradual migration, no `@deprecated` marking". This is a zero-user project with no external consumers needing a transition period.

1. In the same batch, migrate all callers of `getShapeWorldPosition()` directly to `TransformService.getWorldBounds()` or `localToWorld()`
2. Delete `getShapeWorldPosition()` immediately after migration
3. Prioritize replacing call sites in `GroupCommands.ts`, as Group operations are rotation-sensitive

### Disposition of `coordinateConvert.ts`

`worldToGroupLocal` / `groupLocalToWorld` in `src/foundation/geometry/coordinateConvert.ts` are a separate coordinate transform implementation independent of `TransformService`. They accept raw parameters (`worldX, worldY, worldRotation, groupX, groupY, groupRotation`) rather than a `shapeId`, and only handle single-layer parent relationships.

This module is currently only used by `GroupCommands.ts`. Disposition:

1. Migrate `GroupCommands` to use `TransformService`'s matrix methods, because single-layer conversion is insufficient for nested Group scenarios (`coordinateConvert.ts` only handles single-layer parent relationships)
2. Delete `coordinateConvert.ts` directly after migration — do not keep it as a "fallback internal tool", to avoid leaving an entry point that tempts bypassing `TransformService`

### Performance and Caching

Adopting Codex's caching suggestion, but with adjusted implementation:

- Add a per-frame cache in `TransformService`, keyed by `shapeId`, invalidated at the start of each frame or on Store changes
- No caching at the convenience API layer; caching is unified inside `getFullWorldTransform`
- In dev mode, log cache hit rates and hot call sites to assist performance tuning
- v1 uses a per-frame full-clear strategy (simple and reliable); optimize later to per-shape invalidation as needed (invalidate the shape and all its descendants when a shape signal changes)

## Layer 1.5: Screen ↔ Canvas Unification (Execute in Parallel with Layer 1)

> This section was added after the codebase review; neither the Codex nor Gemini reports covered this layer.

### Current State Review

`CameraController` (`src/view/camera/CameraController.ts`) already provides standard coordinate conversion methods:

```typescript
screenToCanvas(sx: number, sy: number): { x: number; y: number }  // (sx - panX) / zoom
canvasToScreen(cx: number, cy: number): { x: number; y: number }  // cx * zoom + panX
```

**Screen → Canvas (input direction): compliant.** All pointer event entry points correctly call `camera.screenToCanvas()`:
- `CanvasContent.clientToCanvas()` — subtracts container offset first, then delegates to `camera.screenToCanvas()`
- `TransformHandles.tsx` — calls `camera.screenToCanvas(e.clientX, e.clientY)` directly
- `ImageShapeView.tsx` — calls via the `clientToCanvas()` helper function

**Canvas → Screen (output direction): shotgun duplication.** `camera.canvasToScreen()` exists and is correct, but 5 View layer components all inline `x * zoom + panX`, none calling it:

| # | File | Inlined Formula | Should Call |
|---|------|-----------------|-------------|
| 1 | `SelectionBox.tsx` | `bounds.x * viewport.zoom + viewport.panX` | `camera.canvasToScreen()` |
| 2 | `AlignmentBar.tsx` | `topLeft.x * viewport.zoom + viewport.panX` | `camera.canvasToScreen()` |
| 3 | `FreehandTrail.tsx` | `p.x * viewport.zoom + viewport.panX` | `camera.canvasToScreen()` |
| 4 | `TextEditorOverlay.tsx` | `s.position.x * zoom + panX` | `camera.canvasToScreen()` |
| 5 | `DOMNodeLayer.tsx` | `x * viewport.zoom + viewport.panX` | `camera.canvasToScreen()` |

All are mathematically correct, but if the `canvasToScreen` formula changes in the future (e.g., adding canvas rotation or DPR correction), all 5 places need manual updates.

**Special note: `DOMNodeLayer.tsx` is the intersection of both layer problems** — it simultaneously inlines parent-chain-walk (Local→World) and canvas→screen conversion (World→Screen), making it the single most duplicated file in the entire coordinate pipeline.

### Missing APIs in `CameraController`

**`getVisibleWorldBounds()`**: `CanvasRenderer.getViewportBounds()` is a private method that calculates the visible area by calling `screenToCanvas` twice. `Minimap.tsx` inlines `-vp.panX / vp.zoom` to compute the same thing. This method should be promoted to a public method on `CameraController`:

> ⚠️ **Review Revision: do not use `window.innerWidth/Height`**
>
> The canvas does not fill the entire window — there are Toolbar, TopBar, RightPanel, and other UI elements. The existing `CanvasContent.clientToCanvas()` subtracts the container offset before calling `screenToCanvas`, confirming the canvas container has its own bounds. `CameraController` should hold a container size signal (set when `CanvasShell` mounts), or accept container size as a parameter.

```typescript
// Option A: accept parameters (stateless, simpler)
getVisibleWorldBounds(containerWidth: number, containerHeight: number): Rect {
  const topLeft = this.screenToCanvas(0, 0);
  const bottomRight = this.screenToCanvas(containerWidth, containerHeight);
  return {
    x: topLeft.x,
    y: topLeft.y,
    width: bottomRight.x - topLeft.x,
    height: bottomRight.y - topLeft.y,
  };
}

// Option B: CameraController holds a containerSize signal (more convenient, consumers don't need to pass params)
// Call camera.setContainerSize(width, height) when CanvasShell mounts
// getVisibleWorldBounds() reads the containerSize signal internally
```

Option B is recommended — `CameraController` is already in the View layer, holding a container size signal does not violate layering rules, and consumers like `Minimap` have a cleaner call.

**`getViewportMatrix(): Mat2x3`**: The current `CameraController` only exposes scalar methods (`screenToCanvas` / `canvasToScreen`), not a matrix. But the combined matrix optimization in the View layer (see "Layer 1.75" below) needs a viewport matrix to pre-multiply with `TransformService.getFullWorldTransform()`. Add:

```typescript
getViewportMatrix(): Mat2x3 {
  const z = this.zoom.value;
  const px = this.panX.value;
  const py = this.panY.value;
  // Screen = World × zoom + pan → Mat2x3 = [zoom, 0, 0, zoom, panX, panY]
  return [z, 0, 0, z, px, py];
}
```

### Why Inlining `canvasToScreen` Is Lower Risk Than Inlining Parent-Chain-Walk

Both are the same pattern (correct infrastructure exists but consumers don't use it), but the risk levels differ:

- The inlined version of parent-chain-walk will produce wrong results once Group rotation is enabled (mathematically not equivalent)
- The inlined version of `canvasToScreen` is currently mathematically fully equivalent to `camera.canvasToScreen()` and will not produce wrong results

Therefore, Screen↔Canvas unification has lower priority than Local↔World, but should still be done in the same batch because:
1. Prevents shotgun-style changes when the formula changes in the future
2. `DOMNodeLayer.tsx` migration touches both layers and shouldn't be split
3. Code intent is clearer after unification — `camera.canvasToScreen(x, y)` is more semantic than `x * viewport.zoom + viewport.panX`

### Canvas→Screen Consumers to Migrate

| # | File | Migration |
|---|------|-----------|
| 1 | `SelectionBox.tsx` | Replace with `camera.canvasToScreen(bounds.x, bounds.y)` |
| 2 | `AlignmentBar.tsx` | Replace with `camera.canvasToScreen(topLeft.x, topLeft.y)` |
| 3 | `FreehandTrail.tsx` | Call `camera.canvasToScreen(p.x, p.y)` inside the map |
| 4 | `TextEditorOverlay.tsx` | Replace with `camera.canvasToScreen(s.position.x, s.position.y)` |
| 5 | `DOMNodeLayer.tsx` | Get world coordinates via `TransformService` first, then call `camera.canvasToScreen()` |
| 6 | `Minimap.tsx` visible area calculation | Replace with `camera.getVisibleWorldBounds()` |

## Layer 1.75: View Layer Coordinate Helpers and Combined Matrix (Execute After Layer 1/1.5)

### Architecture Decision: Do Not Add Screen-Related Methods to TransformService

The Local→World→Screen pipeline in `DOMNodeLayer.tsx` raises a design question: should a `localToScreen` shortcut API be provided?

**Decision: do not put `localToScreen` inside `TransformService`.**

Rationale (see analysis in `是否暴露中间坐标空间.md`):

1. **Responsibility pollution**: `TransformService` is a geometric space system (scene graph transform); `CameraController` is a view system (viewport projection). If `TransformService.localToScreen()` existed, it would mean `TransformService` depends on `CameraController` — a reverse dependency. Mature canvas systems (Figma, tldraw, Konva) all maintain this boundary
2. **World space is the core space and should not be hidden**: collision detection, snapping, alignment, selection box, spatial index, and hit testing all work in World space. If View layer developers habitually use `localToScreen` directly, they will forget World space exists, causing long-term coordinate confusion
3. **CanvasRenderer's matrix stack already proves the correctness of layering**: Canvas 2D's `ctx.translate` + `ctx.scale` is essentially `Local → World → Screen` in two steps handled automatically by the matrix stack. DOM has no matrix stack, so the two steps must be done manually, but the pipeline structure is the same

### The Right Approach: View Layer `coordHelpers.ts`

Add a composition helper module under `src/view/` for exclusive use by the View layer:

```typescript
// src/view/coordHelpers.ts

import type { MShapeId } from '@/src/foundation/id';
import type { Vec2 } from '@/src/foundation/geometry/Vec';
import type { Mat2x3 } from '@/src/foundation/geometry/Mat';
import { matMultiply, matApply } from '@/src/foundation/geometry/Mat';
import type { TransformService } from '@/src/core/editor/TransformService';
import type { CameraController } from './camera/CameraController';

/**
 * Local → Screen combined transform.
 * Internally goes through TransformService.localToWorld → CameraController.canvasToScreen.
 */
export function localToScreen(
  transform: TransformService,
  camera: CameraController,
  shapeId: MShapeId,
  local: Vec2,
): Vec2 {
  const world = transform.localToWorld(local, shapeId);
  return camera.canvasToScreen(world.x, world.y);
}

/**
 * Get the combined Local → Screen matrix.
 * screenFromLocal = viewportMatrix × worldFromLocalMatrix
 *
 * For batch point conversion scenarios (e.g., DOMNodeLayer rendering multiple children),
 * avoids two function calls per point.
 */
export function getScreenTransform(
  transform: TransformService,
  camera: CameraController,
  shapeId: MShapeId,
): Mat2x3 {
  const worldFromLocal = transform.getFullWorldTransform(shapeId);
  const viewportMat = camera.getViewportMatrix();
  return matMultiply(viewportMat, worldFromLocal);
}
```

### Responsibility Layer Summary

| Layer | Module | Responsibility |
|-------|--------|----------------|
| Foundation | `Mat.ts` | Pure matrix math |
| Editor | `TransformService` | Local ↔ World (scene graph transform) |
| View | `CameraController` | World ↔ Screen (viewport projection) |
| View | `coordHelpers.ts` | Local ↔ Screen (composition, no new logic) |

### Performance Value of `getScreenTransform`

The current `DOMNodeLayer` does two steps per Group child: walk the parent chain to get world coordinates, then multiply by zoom/pan to get screen coordinates. `getScreenTransform` pre-multiplies these two steps into one matrix — for multiple children under the same Group, only one matrix multiplication is needed, and each subsequent child only needs one `matApply`. Performance improvement is significant for large numbers of nested nodes.

### Note on Document Space

`是否暴露中间坐标空间.md` mentions the choice between Document Space and World Space. The current project is a single canvas with no artboard/page concept — World Space is Document Space, no additional layering needed. If multiple artboards or region-specific export are introduced in the future, a layer between World and Document will be needed. This decision point is recorded; no action for now.

## Layer 2: Architecture Rule Enforcement (Land in Parallel with Layer 1)

### Hard Rules

> **Rule A (Local ↔ World)**: Forbidden to manually traverse the `parentId` chain in the View/UI layer to calculate coordinates. Manual traversal cannot correctly handle parent rotation and scaling, causing selection box misalignment and collision detection failures. All Local ↔ World calculations must and can only go through `TransformService`.
>
> **Rule B (Canvas ↔ Screen)**: Forbidden to inline `x * zoom + panX` or `(x - panX) / zoom` formulas in the View/UI layer. All Canvas ↔ Screen calculations must and can only go through `CameraController.canvasToScreen()` / `screenToCanvas()`.

### Enforcement Mechanisms

Merging suggestions from both reports, ordered by practical feasibility:

1. **Steering Rule**: Write into `.kiro/steering/` rule files; agents and human developers automatically follow when writing/reviewing code (covers both Rule A and Rule B)
2. **PR Review checklist**: Globally search `view/` directory for `.parentId` traversal and inlined `* viewport.zoom + viewport.panX` formulas; reject on discovery
3. **ESLint/AST check** (adopting Codex suggestion, but lower priority): detect patterns with `parentId` inside `while`/`for` in the `view/` directory. Valuable but non-blocking, as the project currently has no custom ESLint rule infrastructure

> ⚠️ **Review Revision: remove dev-mode runtime guard**
>
> The original plan suggested adding `console.warn` inside `getShapeWorldPosition()`. But under the Big Bang principle, this method will be deleted directly after migration — there is no transition period requiring a runtime guard.

### Comment on Codex's "Training Session" Suggestion

Codex suggested a 30-minute internal sharing session. This suggestion does not apply to the current project — it is a solo/small-team project; Steering Rule is sufficient coverage.

### 6 Consumers to Migrate

| # | File | Current Implementation | Migration Target |
|---|------|------------------------|-----------------|
| 1 | `CanvasEditor.getShapeWorldPosition()` | Accumulates bounds.x/y | Migrate all callers to `TransformService`, then delete directly |
| 2 | `CanvasRenderer.ts` inline ancestor array | ctx.translate + ctx.rotate | Use `TransformService.getFullWorldTransform()` to set canvas transform |
| 3 | `DOMNodeLayer.tsx` inline offset accumulation | Accumulates bounds.x/y | Use `TransformService.localToWorld()` or `getWorldBounds()` |
| 4 | `SelectionBox.tsx` → `unionBounds()` | Inline offset accumulation | Use `TransformService.getWorldBounds()` |
| 5 | `TransformHandles.tsx` → `getParentWorldOffset()` | Fixed but still inline implementation | Use `TransformService.getWorldBounds()` |
| 6 | `GroupCommands.ts` | Calls `getShapeWorldPosition()` + `coordinateConvert.ts` | Use `TransformService` matrix methods |

## Layer 3: Branded Types (Gradual Introduction)

### Adopted Approach

Merging both reports, adopting Gemini's `readonly __brand` approach (simpler than Codex's `unique symbol`):

```typescript
// foundation/geometry/types.ts
export type WorldPoint = { x: number; y: number } & { readonly __brand: 'world' };
export type LocalPoint = { x: number; y: number } & { readonly __brand: 'local' };

export const asWorld = (p: { x: number; y: number }): WorldPoint => p as WorldPoint;
export const asLocal = (p: { x: number; y: number }): LocalPoint => p as LocalPoint;
```

### Comment on Codex's Generic Point Approach

Codex proposed a `Point<Space extends 'local' | 'world'>` generic approach that is theoretically more elegant, but not adopted in this project:

1. The project already has two point type definitions — `Vec2` (`{ x: number; y: number }`) and `Point` (same structure). Introducing a generic Point adds a third, worsening type fragmentation
2. The `readonly __brand` approach has better compatibility with the existing `Vec2` — only needs `as` casting at boundaries, no need to change the entire type system
3. The generic approach displays as `Point<'local'>` rather than `LocalPoint` in IDE hints, slightly worse readability

### Rollout Strategy

1. Introduce branded types on `TransformService` input/output parameters first
2. At mouse event entry points (`CanvasContent.clientToCanvas()`), wrap `e.clientX/Y` as `WorldPoint` directly after camera conversion
3. Old code uses explicit `asWorld` / `asLocal` conversions, no large-scale rewrite
4. New code enforces branded types
5. Long-term optional: introduce `ScreenPoint` branded type to cover Screen space, making the full three-layer coordinate pipeline type-safe

### Comment on Codex's "Don't Enforce Branding Too Early at Library Boundaries"

This suggestion is reasonable but does not apply — this project is not a publicly released library with no external integrators. `TransformService` is an internal API and can be enforced directly.

## Implementation Plan

No timeline. Execute in dependency order; advance to the next step upon completion:

0. Fix `TransformService.localToWorld()` and `worldToLocal()` to use `getFullWorldTransform` instead of `getWorldTransform` (prerequisite for all subsequent migrations)
1. Add `getWorldBounds()` to `TransformService`
2. Add `getVisibleWorldBounds()` and `getViewportMatrix()` to `CameraController`; if using Option B, also add `containerSize` signal and `setContainerSize()`
3. Migrate the 6 Local→World consumers to `TransformService` one by one, including all callers of `getShapeWorldPosition()`
4. Delete `CanvasEditor.getShapeWorldPosition()`
5. Migrate the 5 inlined Canvas→Screen consumers to `camera.canvasToScreen()` one by one
6. Migrate `Minimap.tsx` visible area calculation to `camera.getVisibleWorldBounds()`
7. Create `src/view/coordHelpers.ts`, implementing `localToScreen()` and `getScreenTransform()`
8. Migrate `DOMNodeLayer.tsx` to use `coordHelpers.getScreenTransform()` (resolves both shotgun problems at once)
9. Write Steering Rule (covering both Rule A and Rule B)
10. Introduce Branded Types to `TransformService` and `CameraController` boundaries
11. Delete `coordinateConvert.ts`

> Note: Steps 3 and 5 can be executed in parallel. Step 7 depends on Step 2 (needs `getViewportMatrix()`). Step 8 depends on Steps 3 + 5 + 7 (three prerequisites). Step 0 is the prerequisite for everything and must be completed first.
