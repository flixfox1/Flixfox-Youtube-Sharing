# 坐标转换散落问题 — 诊断报告

> 日期：2026-03-15
> 严重程度：架构级缺陷
> 状态：已诊断，待标准化

## 1. 问题描述

Group 子元素在 Store 中存储 **LOCAL 坐标**（相对于父 Group 的偏移），但 View 层的多个消费方需要 **WORLD 坐标**（画布绝对位置）来渲染和定位。

当前 local→world 转换逻辑被 **6 个不同位置各自独立实现**，没有统一入口。其中 `TransformHandles.tsx` 漏掉了转换，导致 group edit 模式下 handles 与实际渲染位置存在偏移。

## 2. 已发现的 Bug

**现象**：进入 group edit 模式后，子元素的 bounding box / transform handles 与实际渲染位置存在距离偏移。

**根因**：`TransformHandles.tsx` 的 `unionBounds()` 函数直接使用 `shape.bounds.x/y`（LOCAL 坐标）定位 handles，但 CanvasRenderer 和 DOMNodeLayer 使用 WORLD 坐标渲染 shape。偏移量 = 父 Group 的 `bounds.x/y`。

**已修复**：添加 `getParentWorldOffset()` 函数，在屏幕定位时叠加 ancestor 偏移。

## 4. 架构分析

### 已有但未被利用的标准工具

`TransformService`（Editor 层）已经提供了完整的坐标变换 API：

```
TransformService
├── getLocalTransform(shapeId)        → 单个 shape 的本地变换矩阵
├── getFullLocalTransform(shapeId)    → 含 position offset 的本地变换
├── getWorldTransform(shapeId)        → 世界变换矩阵（仅旋转）
├── getFullWorldTransform(shapeId)    → 完整世界变换矩阵（位移+旋转）
├── worldToLocal(point, shapeId)      → 世界坐标 → 本地坐标
└── localToWorld(point, shapeId)      → 本地坐标 → 世界坐标
```

但 View 层的 4 个消费方（DOMNodeLayer、SelectionBox、TransformHandles、CanvasRenderer）**没有一个使用它**，全部自己手写了简化版。

### 为什么会这样？

1. `TransformService` 返回 `Mat2x3` 矩阵，对于只需要简单 x/y 偏移的场景显得"太重"
2. 缺少一个轻量级的 `getAncestorOffset(parentId): Point` 便捷方法
3. 没有架构规则禁止内联实现坐标转换
4. 各组件开发时间不同，互相不知道对方的实现

### 本质问题

**Shotgun Surgery（散弹式修改）**：同一个业务逻辑（parent chain walk）散落在 6 处。任何坐标系相关的变更都需要同时修改 6 个文件，遗漏任何一个就产生 bug。

## 5. 风险评估

### 当前已知风险

- [x] TransformHandles 偏移 — **已修复**
- [ ] 未来新增的 View 组件可能再次内联实现，再次遗漏
- [ ] 如果 Group 嵌套逻辑变更（如支持 Group rotation），需要同时修改 6 处
- [ ] CanvasRenderer 的 ancestor 数组收集逻辑与其他 5 处的简单累加不一致（它额外处理了旋转），如果其他地方也需要处理旋转，又会出现不一致

### 潜在的下一个 Bug

如果未来实现 **Group 旋转**（当前 Group 的 rotation 字段存在但未被所有消费方处理），DOMNodeLayer 和 SelectionBox 的简单 `x += bounds.x` 累加将无法正确处理旋转后的坐标偏移，只有 CanvasRenderer（使用 ctx.translate + ctx.rotate）和 TransformService（使用矩阵）能正确处理。届时将出现更严重的坐标不一致。
