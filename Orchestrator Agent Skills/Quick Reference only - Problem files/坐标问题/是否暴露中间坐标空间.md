这是一个**典型的画布架构设计问题**：
**是否暴露中间坐标空间（World），还是提供跨层快捷 API。**

你的分析已经非常接近成熟架构了。我直接给结论，然后解释原因。

---

# 结论（建议）

**不要把 `localToScreen` 放进核心 Service。**

保持 **三层坐标系统清晰分离：**

```
Local  --TransformService-->  World  --Camera/Viewport-->  Screen
```

然后在 **View 层提供一个组合 helper**：

```ts
function localToScreen(shapeId: MShapeId, local: Point): ScreenPoint {
  const world = transformService.localToWorld(shapeId, local)
  return camera.worldToScreen(world)
}
```

也就是说：

| 层级                | 职责                 |
| ----------------- | ------------------ |
| TransformService  | Local ↔ World      |
| Camera / Viewport | World ↔ Screen     |
| View helper       | Local ↔ Screen（组合） |

**不要把这三个混在一个 service 里。**

---

# 为什么不要把 `localToScreen` 放进 TransformService

### 1️⃣ 职责污染（最重要）

TransformService 本质是 **几何空间系统**。

```
TransformService = scene graph transform
```

Camera / viewport 是 **视图系统**。

```
Camera = how world is projected to screen
```

如果你把 `localToScreen` 放进去：

```
TransformService.localToScreen(...)
```

意味着 TransformService **依赖 camera / viewport**。

架构就变成：

```
TransformService
   ↳ Camera
```

这是反向依赖，长期会很难维护。

很多成熟画布系统都保持这条边界，例如：

* Figma
* tldraw
* Konva

它们都有同样的分层：

```
scene transform
viewport transform
render projection
```

---

# 2️⃣ World 空间其实是核心空间（不要隐藏）

虽然 DOMNodeLayer 觉得 World 很烦，但实际上：

**World 是整个系统唯一稳定的空间。**

因为：

```
Local = 节点内部
World = 场景统一空间
Screen = 视口空间
```

很多逻辑都必须使用 world：

* 碰撞检测
* snapping
* alignment
* selection box
* ruler / guide
* spatial index
* hit testing

如果 View 层习惯直接用 `localToScreen`，
会导致 **大家忘记 world 的存在**。

长期会产生这种 bug：

```
A: localToScreen(...)
B: worldToScreen(...)
C: screenToWorld(...)
```

各种坐标混乱。

---

# 3️⃣ CanvasRenderer 的矩阵栈已经证明了这个分层

你的 `CanvasRenderer` 实际是这样工作的：

```
ctx.save()

ctx.translate(worldX)
ctx.rotate(...)
ctx.scale(...)

ctx.scale(zoom)
ctx.translate(pan)

draw()
```

等价于：

```
Local → World → Screen
```

Canvas 的 matrix stack **只是帮你自动做了两步**。

DOM 没有 matrix stack，所以你才会感觉它是“双重散弹”。

但本质 pipeline **是对的**。

---

# 推荐的 API 结构（工业级版本）

## TransformService

只负责 scene graph transform：

```ts
localToWorld(shapeId: MShapeId, p: LocalPoint): WorldPoint

worldToLocal(shapeId: MShapeId, p: WorldPoint): LocalPoint

getWorldTransform(shapeId: MShapeId): Mat2x3

getWorldBounds(shapeId: MShapeId): Rect
```

---

## Camera / Viewport

只负责 viewport transform：

```ts
worldToScreen(p: WorldPoint): ScreenPoint

screenToWorld(p: ScreenPoint): WorldPoint

getViewportMatrix(): Mat2x3
```

---

## View Helper（推荐新增）

专门给 View 层使用：

```ts
// view/coordHelpers.ts

export function localToScreen(
  shapeId: MShapeId,
  local: LocalPoint
): ScreenPoint {
  const world = transformService.localToWorld(shapeId, local)
  return camera.worldToScreen(world)
}
```

优点：

* View 调用简单
* 不污染核心 service
* 仍然保持 World 概念

---

# 额外一个非常关键的优化（强烈建议）

很多成熟 infinite canvas 系统都会提供 **组合矩阵**：

```
ScreenFromLocalMatrix
```

计算方式：

```
screenFromLocal =
    viewportMatrix
  × worldFromLocalMatrix
```

这样可以避免两次函数调用。

例如：

```ts
getScreenTransform(shapeId: MShapeId): Mat2x3
```

内部：

```
screenFromLocal = viewportMatrix * worldFromLocal
```

使用：

```ts
const mat = coord.getScreenTransform(shapeId)
const p = mat.apply(localPoint)
```

这是性能最好的方式。

在大型文档里会明显更快。

# 最终推荐结构（非常稳定的一种）

```
                TransformService
                (scene graph)
                       │
                       │
Local ───────────────▶ World
                       │
                       │
                 Camera / Viewport
                       │
                       ▼
                    Screen
```

View 层：

```
coordHelpers.ts
```

组合调用。

# 最后一个关键 insight

你发现的这个问题，其实说明你的架构正在向 **Scene Graph + Camera Model** 演进。

这正是：

* Unity
* Three.js
* Figma

这些系统的经典结构：

```
Object Space
   ↓
World Space
   ↓
View Space
   ↓
Screen Space
```

你现在其实只差一步：
**把 viewport transform 正式抽象成 Camera。**

一旦这样做，很多代码会自动变干净。
